# Graupl themes

Create a distinct visual theme using Graupl's existing CSS. Write the theme in CSS only. Do not write or change Sass, Graupl's source, component JavaScript, application logic, or theme-switching JavaScript. A demo may use Graupl's existing component generators with the initialization and configuration documented for the installed version. Do not change their implementation as part of theming. A light/dark toggle, persistence, and other controls belong to the application. Use the existing mode mechanism if there is one.

## Workflow

1. Read the project's instructions and identify the target Graupl version. For a new theme, start with the current `latest` release of `@graupl/graupl` on npm unless the project specifies a version. For an existing theme, check the version or revision its preview loads. Inspect the target version's compiled CSS, documentation, and existing markup to verify the supported custom properties, fallback values, selectors, generators, and colour-mode mechanism. Read `references/graupl-css.md` for a verified example tied to a specific revision. If the source is unavailable, say what could not be verified.
2. Use the request to guide the palette, typography, and parts of Graupl you style. Choose styles that give the theme its own look. If the user provides a reference, distinguish inspiration from official branding and respect asset licensing. Design related pieces as a whole, including accordion headers and containers, tab controls and panels, and disclosure toggles and content. Check how their alignment, spacing, borders, and corners fit together in each state. Give borders and enclosures a purpose, such as structure or a state cue, rather than adding visual weight by default. Keep borderless controls identifiable with clear hover and keyboard-focus states. Do not turn one theme's visual choices into universal rules.
3. Load a separate theme stylesheet after Graupl where the project permits. Before changing a style, check whether it comes from the theme, a Graupl fallback, or another layer. Inspect the relevant declarations and cascade before styling. Whenever a CSS property is controlled by a Graupl custom property, set that custom property instead of overriding the CSS property directly.

   Set custom properties at the highest scope that produces the intended result. Start at `:root`. Use `.card` for changes limited to cards and `.card-header` for changes limited to card headers. Move to a narrower scope only when required by the design or cascade. Check computed values because component-local declarations and inherited custom-property aliases can prevent a root override from taking effect.

   Add targeted CSS only where no applicable custom property controls the value. Decorative pseudo-elements are allowed. Keep the theme removable and avoid unnecessary specificity and `!important`.
4. Establish the base design tokens first. Inspect Graupl's base and theme properties for spacers, font sizes, font weights, colours, typography, and other reusable values. Explicitly declare the base properties and complete existing spacer scale in the theme, even when retaining Graupl fallback values, so they are available for direct reference. Use the target version's verified fallback values for unchanged tokens.

   Resolve base-scale arithmetic into explicit values rather than copying fallback `calc()` expressions or deriving each entry from another base token. Keep relative units such as `rem`. Read the base-value guidance in `references/graupl-css.md` for inheritance behaviour and exceptions.

   Reference spacer properties for padding, margins, gaps, and other spacing where appropriate. Reference existing base font-weight and font-size properties for component values rather than repeating raw values. Apply the same pattern to colours and other base properties. Leave component defaults in place when their existing fallback chains already produce the intended result. Ensure every `var()` reference resolves or has a valid fallback. Use Graupl property names verified in the target version and check how they inherit. Do not invent Graupl properties. If a needed token does not exist, define a clearly theme-owned token and reuse it.
5. Use the palette families and shade tokens the target version supports. Define the full relevant scales. Use Graupl's existing colour-mode mechanism. In custom styling, use the matching `--graupl-theme-active--<palette>--<shade>` property when its mapping gives the intended colour in both modes. Use `light-dark()` for custom pairs that the active palette does not provide. Check the rendered colours for base, hover, focus, active, selected or current, expanded, invalid, visited, and disabled states where applicable. Preserve a visible keyboard focus indicator that follows the focused control's shape without clipping or disappearing against its surroundings.

   Check the indicator's shape and position in open and closed states, especially for controls inside rounded containers. Apply the focus review below when indicators extend beyond a control or sit near neighbouring controls. Distinguish meaningful states through text, shape, borders, icons, or other cues in addition to colour where possible. Do not introduce an independent JavaScript toggle.
6. Preserve component markup, semantics, interaction, focus order, and existing JavaScript. A demo can use Graupl generators with documented initialization and configuration. Do not replace them with custom interaction code. When reviewing a preview, check the relevant [ARIA Authoring Practices Guide pattern](https://www.w3.org/WAI/ARIA/apg/patterns/) for keyboard interaction and focus behaviour. Use [WAI-ARIA](https://www.w3.org/TR/wai-aria/) to check the roles, states, and properties the preview uses.

   Media and container queries are appropriate for responsive design. Apply the same custom-property and scope rules inside them. Review how the layout and controls work together at each breakpoint. Check the visual weight and grouping of mobile navigation toggles and expanded menus rather than assuming a desktop treatment works whenever it fits.

   Respect reduced motion, forced colours, contrast and transparency preferences where applicable and supported. Avoid unnecessary animation, and do not rely on motion alone to communicate meaning. Reduce nonessential movement without hiding content or breaking component transitions. Decorative overlays must not intercept input or conceal content or focus indicators. Keep essential labels in the markup. In forced colours, check that content and controls remain readable when backgrounds or shadows disappear. Treat reduced motion as a user preference and check which WCAG criteria apply to the specific animation.
7. Test the theme in the browser. Use a keyboard to inspect focused, expanded, and selected states at wide and narrow sizes. Check the relationships between component parts as well as each part in isolation.

   Check both modes and applicable interaction states against their rendered adjacent backgrounds, including text, controls, focus indicators, and any translucent overlays. Apply the WCAG 2.2 criteria for [text contrast](https://www.w3.org/TR/WCAG22/#contrast-minimum) and [non-text contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast), distinguish inactive-control exceptions, and do not assume hover and resting colours must contrast with each other.

   Verify keyboard use and check [Focus Visible](https://www.w3.org/TR/WCAG22/#focus-visible) and [Focus Not Obscured (Minimum)](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum). Check non-colour state cues against [Use of Color](https://www.w3.org/TR/WCAG22/#use-of-color). Check narrow and wide layouts. Where applicable, check [Reflow](https://www.w3.org/TR/WCAG22/#reflow) and [Resize Text](https://www.w3.org/TR/WCAG22/#resize-text). Verify theme removal. Exercise reduced motion and forced colours where tools permit, plus other relevant user preferences. Run applicable CSS checks. Record the checks you ran and their limits. Claim accessibility conformance only after verifying the applicable criteria. Report component bugs separately rather than changing JavaScript outside the task.

## Focus review

- Inspect the entire focus area, including the ring, its offset, and any transparent gap between the indicator and the control. Check what neighbouring borders, backgrounds, or content show through that gap. A visible ring alone does not establish a clean or readable focus state.
- Focus adjacent controls in both directions, including previous and next controls in a row or stack. Check both light and dark modes at wide and narrow sizes rather than testing only an isolated control.
- Diagnose stacking order, outline offset, spacing, transparency, and clipping separately. Raising the focused control can fix paint order without changing what shows through a transparent gap. Choose a fix for the cause you found. Set the outline offset to zero only where it addresses the problem.
- When several controls need the same fix, prefer a shared Graupl focus property at the widest scope that works. After changing it, check varied affected controls, such as buttons, links, navigation toggles, accordion headers, and tabs. Narrow the scope when the shared change causes a regression.
- Reproduce the exact reported symptom before editing and repeat the same interaction and visual check afterward. Verify the neighbouring edges and gap as well as the ring. If the symptom cannot be reproduced or the result cannot be inspected, report that limit. To verify the fix, check the specific interaction and visual result.

Deliver the CSS and any requested preview or integration instructions. State the Graupl version checked, how to load and remove the theme, and test limitations. Do not include a mode toggle in the theme deliverable unless the user separately requests one.
